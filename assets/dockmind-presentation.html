02 · HLD · Receipt lifecycle

One state machine, two terminal states

CAPTUREDphoto saved, reading
→
EXTRACTEDread and PO resolved
→
CONFIRMEDterminal
↳
NEEDS_MANUALread failed or PO unresolved
→
DISPUTEDterminal, with reason

Only the clerk moves a receipt forward

A NEEDS_MANUAL receipt can be corrected, given a PO, or disputed. It cannot be confirmed until a PO is assigned.

Never a 500, never a dropped receipt

Model failure or garbage output lands in NEEDS_MANUAL with the photo kept. poNumber is always null in that state.

02 · HLD · Guarantees

Three promises the design keeps

🔁

Idempotent capture

The phone makes one Idempotency-Key at capture time and reuses it on every retry, even after a kill. The server has a unique constraint on that key.

📴

Offline tolerant

Every capture goes through the local queue first, online or not. The queue drains in order when the network returns.

🧮

Deterministic decisions

Discrepancies come from one pure matcher. The model never does arithmetic and never decides a discrepancy.

02 · HLD · End to end

From shutter tap to a decision

  1. Phone copies the photo to app storage, makes the key, writes a SQLite row as WAITING. This happens before any network call.

  2. Queue uploads the head item (A4) with its key. The server answers 202 with the receipt as CAPTURED.

  3. Server saves the receipt and photo in one transaction, then reads the note on a background thread.

  4. Reader returns JSON. The validator cleans it, checks the PO and supplier, and clamps confidence. The result is saved as EXTRACTED or NEEDS_MANUAL.

  5. Phone polls A3 and shows the lines, the discrepancy chips and the aiNote.

  6. Clerk corrects quantities (A5) or assigns a PO (A8), ticks flagged lines, then confirms (A6) or disputes with a reason (A7).

03 · LLD · Offline queue

Four states, one row per capture

WAITINGsaved, not sent
→
UPLOADINGrequest in flight
→
SYNCEDhas receiptId
↳
FAILED400 / 413, manual retry

Retry rules

Network errors, 5xx and timeouts go back to WAITING with exponential backoff: 2 s, doubling, capped at 60 s. A 400 or 413 goes to FAILED with a plain reason and a retry button.

Recovery and ordering

On start, any row left in UPLOADING returns to WAITING with the same key. Uploads are strictly in order, one at a time, and a newer item never overtakes one that is backing off.

03 · LLD · Drain loop

How the queue drains

  • Single flight. A drain call during a run sets a rerun flag. It does not start a second run.

  • Wake triggers. Connectivity returns, the app comes to the foreground, or the clerk taps retry. Each wake clears backoff timers and drains.

  • Storage failure. If SQLite throws, the queue logs it and retries after 60 s instead of stopping for good.

  • Key stays fixed. Every attempt, including a manual retry, sends the same key, so the server returns the same receipt.

Upload attempt, simplified

while (isOnline()) {
  head = first WAITING item
  if (head.nextAttemptAt > now) schedule(wait); return
  // mark UPLOADING, bump attempts, publish
  try {
    receiptId = await upload(head)   // A4, same key
    store(SYNCED, receiptId)
  } catch (e) {
    outcome = classify(e)
    retry ? WAITING + backoff : FAILED
  }
}

03 · LLD · Review and decide

The app renders, the server decides

Reviewing a receipt

After upload, the review screen polls A3. A slow read shows "Still reading the note, this can take 30 seconds". Each line shows ordered against received, a colored discrepancy chip, its confidence, and the aiNote.

Corrections go through A5. The screen then shows the server's recalculated discrepancy and delta. The app has no discrepancy logic of its own.

Confirm is gated in the client

confirmBlocker() returns the reason Confirm is off, in plain words:

  • Receipt not EXTRACTED or NEEDS_MANUAL
  • poNumber null: pick the PO first (A8)
  • Each flagged line not yet ticked
  • Flagged receipt with a PO: tick the PO too

The server still enforces every rule. The client check is about making the clerk look.

Dispute and repeats

Dispute needs a non-blank reason, up to 2000 characters. Confirm and dispute are both safe to tap twice, so a double tap or a retry after a timeout cannot change the result.

04 · LLD · Backend structure

Five packages, one direction of dependency

apicontrollers, error map
→
servicecapture, runner, receipts
→
ai · matchingreader and pure matcher
→
domainJPA entities, repos

Key classes

CaptureService handles A4 and idempotency. ExtractionRunner runs the reader off the request thread. ReceiptService holds the lifecycle and every clerk action. Matcher is pure, with no Spring and no database.

Why this shape

The matcher can be unit tested in isolation, and the reader can be swapped without touching the lifecycle. The validator sits between them, so nothing unchecked reaches ReceiptService.

04 · LLD · Capture (A4)

Idempotent capture in five checks

  1. Key. Trim the Idempotency-Key. It must be 1 to 255 characters, or 400.

  2. Bytes, not headers. Sniff JPEG or PNG magic bytes. A declared type proves nothing.

  3. Replay. Look up the key. If found, return the existing receipt with 200.

  4. Create. Save the receipt and image in one transaction. Flush right away so a duplicate key shows up here.

  5. Race. If the unique key is lost to a concurrent request, catch the error and return the winner's receipt.

Why it's safe

The unique constraint is the real guard. The lookup is a fast path. Two identical requests at the same moment can't both create a receipt.

After creation, ExtractionRunner.submit() starts the read and the controller returns 202 with lines: [].

04 · LLD · Extraction pipeline

Read, validate, then save

ExtractionRunnerexecutor thread
→
ExtractorLlm or Fixture
→
ExtractionValidatorone path for all output
→
applyExtractionrow lock, CAPTURED only

Validator rules

  • Strip markdown fences and any text around the JSON
  • Coerce strings to numbers, including "1,072.5 kg"
  • Clamp confidence to 0..1; "95%" reads as 0.95; missing counts as 0
  • Resolve the PO only if the supplier also agrees
  • Clear any poLineId that is unknown or on another PO

Failure paths all end in NEEDS_MANUAL

  • Timeout, HTTP error, or exception in the reader
  • Unusable output, or a note with no lines
  • A line with an unreadable, negative or huge quantity

applyExtraction returns early unless the receipt is still CAPTURED, so a re-run can't overwrite later clerk work.

Recovery

On startup, every receipt still CAPTURED is read again. A crash between capture and extraction loses nothing.

04 · LLD · Matching

Four rules, applied in order, per line

#ConditionResult
1No PO line linkedUNKNOWN_ITEM delta null
2Linked, unit differsUNIT_MISMATCH delta null
3Received equals 0NOT_DELIVERED delta = −ordered
4Received vs orderedSHORT MATCH OVER

Before the rules

Units are normalized first: KGS and kg become KG, CASES becomes CASE, EACH and PCS become EA. Descriptions are compared in lower case with punctuation removed.

Linking and missing lines

Lines link by exact description first, then by a shortened name when only one PO line fits. Every PO line absent from the note is added as NOT_DELIVERED, by code.

needsReview: confidence below 0.80 and not corrected by the clerk.

04 · LLD · PO resolution and clerk actions

A PO number alone is not enough

The cross-check

A PO is resolved only when poNumber exists and the note's supplier matches that PO's supplier. Matching ignores case, punctuation, and suffixes such as Ltd, Co and Inc.

PO-4503 and PO-4513 differ by one digit. The supplier check is what separates them.

On a mismatch, poNumber is null, every link is cleared, and the receipt goes to NEEDS_MANUAL.

What the clerk can change

ActionRule
A5 correctClerk's quantity wins; keeps aiQty; recomputes
A8 assign POOnly when unresolved; sets confidence to 1.0; a different PO returns 409
A6 confirmNeeds a resolved PO; repeat returns 200
A7 disputeNon-blank reason; repeat keeps the first reason

Concurrency

Every clerk action and every extraction write reads the receipt with a PESSIMISTIC_WRITE lock. A simultaneous confirm and dispute cannot both succeed.

04 · LLD · Data model

Five tables, one photo per receipt

purchase_orders  id · po_number · supplier · status
   └─ po_lines  id · po_id · sku · description
                  ordered_qty · unit

receipts  id · status · idempotency_key UNIQUE
                po_number · supplier · delivery_note_no
                ai_note · overall_confidence · po_confidence
                dispute_reason · clerk · created_at
   ├─ receipt_lines  id · po_line_id ?
   │      description · ai_qty · received_qty
   │      unit · confidence · discrepancy · delta
   │      corrected_by_clerk · needs_review
   └─ receipt_images  receipt_id · data · mime_type

Design notes

  • Two quantities per line. ai_qty keeps what the model read. received_qty is the clerk's number once corrected.
  • Idempotency key is unique, so the database enforces replay safety.
  • Photo sits in its own table, in the same transaction as the receipt.
  • Lines link to PO lines only through po_line_id, which is cleared when invalid.
  • Confirming a receipt does not close its PO, since a PO can arrive in several deliveries.
